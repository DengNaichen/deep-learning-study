# 从截图集合到可追溯的观察记录

本轮对应 refine 路线的第 2 项：记录过程事实，并把事件和图像关联起来。没有接模型，也没有实现推导分析。

## 借鉴 pi 的什么

实现前阅读了本机安装的 pi 文档：`README.md`、`docs/how-pi-works.md`、`docs/sessions.md`、`docs/session-format.md`。这里借鉴的是：

1. **小核心、明确边界**：状态源产生事件，日志保留事实，组装器构建上下文，界面负责展示。不增加 agent 运行时或插件系统。
2. **记录和上下文不是同一回事**：pi 从 session entries 构建 model context；这里从观察日志和快照构建 `LearningContext`。以后可以调整选择策略，而不改写原始观察。
3. **可追溯**：记录具有稳定 ID 和顺序信息，投影后的内容仍能追查来源。

没有照搬 pi 的会话树、分支、压缩摘要或持久化机制。当前日志是**有保留上限的线性内存日志**，不是永久的 append-only 数据库。导出的 JSONL 是本原型自己的格式，不能直接作为 pi session 导入。

## 真实记录的事件

| 类型 | 含义 | 不意味着什么 |
|---|---|---|
| `captureStarted` | 开始观察本 App 的状态变化 | 不是恢复此前未记录的历史 |
| `toolUseBegan` | PencilKit 通知开始使用笔迹工具 | 不代表已经画出一笔 |
| `drawingChanged` | 收到笔迹修改回调，修订号更新 | 不等于完成一个公式或一道题 |
| `toolUseEnded` | 工具使用正常结束 | 不代表学习者完成了思考 |
| `toolUseInterrupted` | 应用非活跃等原因令工具状态被中断 | 不是正常落笔结束回调 |
| `selectionChanged` | 选区设定、改变或清除 | 不代表该区域有错误 |
| `editorModeChanged` | 书写／橡皮／框选模式切换 | 切换橡皮不等于已经擦除 |
| `frameRetained` | 一份图像进入保留历史 | 不代表每个系统视频帧都被保存 |
| `captureStopped` | 停止接收观察事件和新帧 | 不保证系统异步录屏清理已经完成 |
| `contextPrepared` | 显式请求上下文预览，取得最新现场 | 不等于已经把问题提交给模型 |

不记录每次输入问题时的字符变化。问题正文只放进用户请求组装的上下文，不放进原始事件 JSONL。

## 为什么不使用 SwiftUI `onChange` 收集事实

SwiftUI 可以把同一轮中的多次状态变化合并成一次界面更新。若依赖界面渲染收集事件，可能漏掉 `书写 → 橡皮 → 书写` 之类的中间状态。

现在由 `NotebookStore` 在状态修改处同步发送 `NotebookObservation`，`ContextRecorder` 仅在已经开始记录时同步订阅。没有线程跳转或等待下一次渲染：

```text
PencilKit 回调 / 用户操作
          ↓
NotebookStore 同步发布事实
          ↓
ObservationLog 追加条目 ──────┐
                            ├─ ContextAssembler → LearningContext → 检查器
定时取得图像 → ContextHistory ┘
```

相同模式／选区／工具状态的重复赋值不重复记事件。自动清除选区时，先完成笔迹与修订号更新，再发布具有一致最终状态的修改事件和选区事件。

## 事件和图片如何对应

每条事件具有：

- `id`：稳定 UUID。
- `sequence`：日志内单调递增的追加序号；不靠系统时钟来排序。
- `occurredAt`：事件时间。JSON 导出使用 ISO 8601 秒级时间，秒内顺序以序号为准。
- `captureID`：来自哪次开始／停止记录；显式预览时可能为空。
- `source`、`kind`：事件来源和种类。
- `document`：可用时的笔记 ID、修订、模式、选区、工具是否仍在使用。
- `frameID`：图像保留／当前上下文预览事件所指的图片。

同步生成的笔记图像带 `eventCursor = { journalID, throughSequence }`：表示该文档快照截至哪条观察事件。随后追加的 `frameRetained` 指向这张图像。

**ReplayKit 图像的 `eventCursor` 和 `document` 保持为空。** 本 App 的笔记事件仍可以被记录，但视频帧异步到达，不能把“刚收到的屏幕图像”强行关联为“当前文档修订的截图”。

`currentDocument` 每次组装都重新生成，链接到该次 `contextPrepared`。组装完成后日志和图像都是值快照，后续记录或清空不会改变已经打开的预览。

## 有上限、允许缺口，但不隐藏缺口

- 默认最多保留 256 条事件，最大年龄沿用 600 秒；参数在 `PrototypeConfiguration.Context` 中命名。
- 在追加、采样或组装时检查过期记录；不会后台启动永久定时器清理。
- 淘汰记录不会重新编号剩余事件，导出包含淘汰数量与最后序号。
- 清空历史同时清空图片和事件，并生成新的 `journalID`，避免新旧序号混淆。
- 图片和事件采用独立预算。因此可能还留有图片，而边界事件已淘汰；也可能还留有事件，而图像已不在当前包中。检查器明确标记这些情况。
- `drawingChanged` 的频率由 PencilKit 回调决定，256 条并不保证覆盖固定分钟数。若以后需要更长历史，应单独设计持久化或投影摘要，不把原始事实偷偷合并成猜测。

例如五秒内写完又擦掉，两张取样图都可能为空白。事件能证明期间收到过两个修订变化及相应工具状态，**不能还原已经擦掉的公式**，因为日志没有保存每条笔画的几何数据。

## 隐私与生命周期

记录关闭时不订阅普通编辑事件。显式点击“上下文”仍会创建一条 `contextPrepared` 并取得当前页面，但不会启动持续观察。

停止时先取消订阅，再执行系统异步清理。若停止时工具仍在使用，只记录边界状态，不伪造 `toolUseEnded`。非活跃导致的工具中断在停止观察前记录为独立事件。

原始 JSONL 不含图像字节和问题正文，但含文档 ID、选区、修订、操作时间等元数据；分享前仍应检查。完整上下文 JSON 包含图像、事件和问题。两者都只通过用户主动导出保存，不自动落盘或上传。

## 如何试

1. 选择“笔记内容”，开始记录。
2. 连续书写、切换橡皮、擦除；也可以在一个五秒间隔内完成这些操作。
3. 点击“上下文”，切换到“事件”。
4. 检查追加顺序、工具状态和修订变化；切回“图像”查看快照上的事件边界。
5. 可导出完整上下文 JSON，或仅导出原始事件 JSONL。视图切换本身不改变完整 JSON 的导出范围。

格式变更：完整上下文升级为 `schemaVersion = 2`；原始日志格式单独为版本 1。原来的单次选区请求格式不变。本原型尚无旧上下文导入器，因此未实现 v1 上下文到 v2 的迁移。

## 验证与下一步

新增测试覆盖同一轮状态变化不合并、无效重复赋值、写后擦除、工具中断、停止后不再观察、重开会话、帧／事件关联、日志上限及过期、JSONL 往返、上下文组装不改写原始记录。UI 测试覆盖进入事件视图。
